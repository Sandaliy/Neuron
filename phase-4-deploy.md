# Этап 4 — что осталось руками

Код написан, типы проходят, линт чистый, тесты зелёные. Осталось то, что машина сделать не может:
завести Google OAuth, выдать паролей двум ролям базы, накатить миграции на боевую базу и выложить.

Делай по порядку. После каждого шага написано, что должно получиться.

---

## Шаг 1. Google OAuth, 20 минут

Это первая часть `phase-4.md`, она не изменилась. Пройди её и добавь в `.env`:

```
GOOGLE_CLIENT_ID=скопированный client id
GOOGLE_CLIENT_SECRET=скопированный client secret
```

**Адреса, которые Google просит.** Redirect URI сейчас такие:

```
http://localhost:8787/api/auth/callback/google
https://твой-api.vercel.app/api/auth/callback/google
```

JavaScript origins:

```
http://localhost:5173
https://твой-веб-адрес.vercel.app
```

Точный адрес API посмотри в панели Vercel, у проекта с API. Веб-приложения ещё нет, так что второй
origin можно добавить и сейчас, и на пятом этапе.

**Можно и не делать сейчас.** Сервер запускается без этих двух переменных и просто не показывает вход
через Google. Появятся — появится и он. Только обе сразу: одна без другой отвергается на старте, потому
что иначе кнопка есть, а работать она не будет, и ошибка вылезет уже на стороне Google.

## Шаг 2. Две роли базы вместо одной

```bash
pnpm db:migrate
```

**Должно быть:** список таблиц, среди них `rate_limits` и `sync_conflicts`.

Эта миграция создаёт вторую ограниченную роль, `neuron_auth`, и урезает права первой. Пароля у новой
роли пока нет, войти она не может.

```bash
pnpm db:role
```

**Должно быть:** четыре строки, по две на роль, и обе про то, что роль теперь может входить и не
обходит изоляцию. В `.env` появится `DATABASE_URL_AUTH`, а `DATABASE_URL` перезапишется новым паролем.

> Пароли обеих ролей меняются. Пока не обновишь их на Vercel (шаг 5), развёрнутый сервер будет
> отвечать ошибкой базы. Это нормально и чинится тем же шагом 5.

**Зачем вторая роль.** Раньше приложение могло переписать любую строку в таблице `user`, включая чужую
почту, и прочитать любую строку в `account`, где лежат хеши паролей. Никто этого не делал, но
возможность была. Одной ролью два пути не различить: любой флаг вида «сейчас я вхожу в систему»
приложение может выставить и в любой другой момент. Разные пароли — различить можно.

## Шаг 3. Проверь локально

```bash
pnpm dev
```

**Должно быть:** `api listening on http://localhost:8787`.

**Если пишет, что `DATABASE_URL_AUTH` отсутствует** — второй шаг не доделан, вернись к `pnpm db:role`.

Проверь, что сервер жив и видит ли он Google:

```bash
curl -s http://localhost:8787/health
```

**Должно быть:** `{"status":"ok","time":"...","google":true}`. `google:false` означает, что ключей в
`.env` нет — если ты пропустил первый шаг, так и должно быть.

## Шаг 5. Vercel

Панель Vercel → проект с API → **Settings** → **Environment Variables**.

Должно быть ровно это:

| Переменная             | Значение                             |
| ---------------------- | ------------------------------------ |
| `DATABASE_URL`         | строка из `.env`, роль `neuron_app`  |
| `DATABASE_URL_AUTH`    | строка из `.env`, роль `neuron_auth` |
| `BETTER_AUTH_SECRET`   | без изменений                        |
| `BETTER_AUTH_URL`      | без изменений                        |
| `APP_ORIGIN`           | без изменений                        |
| `GOOGLE_CLIENT_ID`     | если делал первый шаг                |
| `GOOGLE_CLIENT_SECRET` | если делал первый шаг                |

**Не должно быть `DATABASE_URL_OWNER`.** Владелец нужен только для миграций и для удаления аккаунтов, с
твоего компьютера. На сервере он не нужен вообще, и это единственная переменная, попадание которой туда
имеет значение: владелец обходит всю изоляцию.

Проверить, что строка правильная, можно по началу: у `DATABASE_URL` пользователь `neuron_app`, у
`DATABASE_URL_AUTH` — `neuron_auth`.

Дальше обычный деплой:

```bash
git push
```

**Должно быть:** сборка проходит, и

```bash
curl -s https://твой-api.vercel.app/health
```

отвечает `{"status":"ok",...}`.

## Шаг 6. Проверки из phase-4.md

**Проверка 1 (дыры третьего этапа).** Уже закрыты и проверены тестами. Посмотреть можно так:

```bash
pnpm vitest run --project api src/db/isolation.test.ts
```

Там три группы: что может роль приложения, что может роль входа, и что нельзя сделать с журналом
ответов. В частности — что приложение не удалит отзыв, даже выставив тот самый флаг, которым это
делалось раньше.

**Проверка 2 (сервер не верит клиенту).** Тест называется «stores its own computation, not the one the
client sent»:

```bash
pnpm vitest run --project api src/routes/reviews.test.ts
```

**Проверка 3 (повтор безвреден).** Там же, «treats the same review id twice as one answer».

**Проверка 4 (вход через Google).** Вот тут неудобство, и его стоит назвать прямо: страницы `/spike`
больше нет, её удаление — пункт 8 промта этапа 4, а веб-приложение появится только на пятом этапе. То
есть кнопки, на которую можно нажать, сейчас в природе не существует.

Проверить поток всё же можно, руками. Попроси у сервера ссылку:

```bash
curl -s -X POST https://твой-api.vercel.app/api/auth/sign-in/social -H "content-type: application/json" -d "{\"provider\":\"google\",\"callbackURL\":\"https://твой-api.vercel.app/health\"}"
```

**Должно быть:** JSON со ссылкой `url`, начинающейся на `https://accounts.google.com/`. Открой её в
браузере.

**Должно быть:** знакомый экран выбора аккаунта, потом возврат на `/health`. Значит, Google настроен и
callback работает.

**Если пишет `redirect_uri_mismatch`:** адрес в консоли Google не совпадает с реальным до символа.
Скопируй тот, что в тексте ошибки, и добавь его в консоль.

По-человечески эта проверка делается на пятом этапе, когда появится экран входа. Сейчас она только
подтверждает, что ключи и адреса верные.

**Проверка 5 (чужие данные).** Полноценно тоже ждёт пятого этапа: без интерфейса второй аккаунт не
завести иначе как запросами. Изоляция при этом проверена с двух сторон в `isolation.test.ts` — и через
слой доступа, и напрямую по базе, мимо всего кода.

**Проверка 6 (человеческие ошибки).** Формат ошибок изменился, и это осознанно. Сервер больше не
присылает английских предложений: он присылает код, который клиент переведёт на нужный язык.

```bash
curl -s https://твой-api.vercel.app/decks
```

**Должно быть:**

```json
{ "error": { "code": "not_authenticated", "status": 401, "correlationId": "019f..." } }
```

**Не должно быть:** стектрейсов, названий таблиц, кусков SQL. `correlationId` — это то, по чему строку
можно найти в логах Vercel, если что-то пойдёт не так и захочется понять, что именно.

**Проверка 7 (секрет владельца).** Она же пятая строка шага 5. `DATABASE_URL_OWNER` на Vercel быть не
должно.

## Что появилось нового, кроме этапа

**`pnpm db:erase`.** Удаление аккаунта теперь ничего не удаляет: оно обезличивает человека, убирает
пароль и сессии и помечает строку. Настоящее удаление происходит через тридцать дней, этой командой, с
твоего компьютера. Она единственная во всём проекте удаляет отзывы. Запускать по желанию, ничего не
сломается, если не запускать никогда.

**`/docs`.** Описание API в формате OpenAPI, сгенерированное из тех же схем, которыми проверяются
запросы, так что разойтись с кодом оно не может. Отдаётся только тем, кто вошёл.
